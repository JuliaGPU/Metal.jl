Arrays and memory

See Arrays for array operations and Memory for storage modes, memory sharing and allocation.

Array types

Metal.MtlArray — Type
MtlArray{T,N,S} <: AbstractGPUArray{T,N}

An N-dimensional array of elements of type T in GPU memory with storage mode S, either Metal.SharedStorage or Metal.PrivateStorage. The storage mode defaults to shared, which can be changed with the default_storage preference.

MtlArray{T}(undef, dims...)MtlArray{T,N,S}(undef, dims...)MtlArray(A::AbstractArray)MtlArray{T}(A::AbstractArray)

Allocate an uninitialized array, or copy A to a new array, converting its elements to T when given. Unlike mtl, MtlArray(A) keeps the element type of A. Element types have to be stored inline, and cannot contain Float64, Int128 or UInt128 values, which Metal doesn't support.

julia> a = MtlArray([1f0, 2f0, 3f0])3-element MtlVector{Float32, Metal.SharedStorage}: 1.0 2.0 3.0julia> Array(a .* 2)3-element Vector{Float32}: 2.0 4.0 6.0

Metal.mtl — Function
mtl(A; storage=Metal.SharedStorage)

Copy A to the GPU, with storage mode storage (Metal.SharedStorage or Metal.PrivateStorage).

This is an opinionated GPU array adaptor, which may alter the element type T of arrays:

  • For T<:AbstractFloat, it makes a MtlArray{Float32} for performance and compatibility reasons (except for Float16).
  • For T<:Complex{<:AbstractFloat} it makes a MtlArray{ComplexF32}.
  • For composite element types (e.g. SVector{2,Float64}), Adapt.jl recursively converts Float64 scalars to Float32 via adapt_structure/adapt_storage dispatch.
  • For other isbitstype(T), it makes a MtlArray{T}.

By contrast, MtlArray(A) never changes the element type.

Uses Adapt.jl to act inside some wrapper structs.

Examples

julia> mtl(ones(3)')1×3 adjoint(::MtlVector{Float32, Metal.SharedStorage}) with eltype Float32: 1.0  1.0  1.0julia> mtl(zeros(1,3); storage=Metal.SharedStorage)1×3 MtlMatrix{Float32, Metal.SharedStorage}: 0.0  0.0  0.0julia> mtl(1:3)1:3julia> MtlArray(1:3)3-element MtlVector{Int64, Metal.SharedStorage}: 1 2 3

Linear algebra

Metal.matmul_alg — Constant
Metal.matmul_alg

A ScopedValue that selects the algorithm LinearAlgebra.mul! (and *) uses for MtlArray matrix-matrix and matrix-vector products:

  • :auto (default): MPSGraph where it supports the operands, otherwise :native.
  • :MPSGraph: MPSGraphs.matmul! and MPSGraphs.matvecmul!.
  • :MPS: MPS.matmul! and MPS.matvecmul!.
  • :native: the best of Metal.jl's own kernels for the operands, of :tensor, :simd and :scalar.
  • :tensor: a Metal 4 tensor-operations kernel, for plain C = A*B products of Float16, Float32 or BFloat16 matrices; only matrix-matrix products.
  • :simd: a SIMD-group matrix kernel.
  • :scalar: a kernel without SIMD-group matrices, for any element type.
  • :GPUArrays: the generic GPUArrays.jl kernel.

An algorithm that doesn't support the operands throws an error. Set it for a block of code with with, from Base.ScopedValues (on Julia 1.10, from the ScopedValues.jl package):

using LinearAlgebra, Base.ScopedValuesA = Metal.rand(Float32, 64, 64); B = Metal.rand(Float32, 64, 64)C = with(Metal.matmul_alg => :MPS) do    A * Bend

Storage modes

The storage mode of an array decides whether the CPU can access its memory. See Apple's Choosing a resource storage mode for Apple GPUs.

Metal.SharedStorage — Type
Metal.SharedStorage

The shared storage mode (MTLStorageModeShared), the default for MtlArrays: the memory is accessible from both the CPU and the GPU. Indexing such an array from the CPU, or wrapping it as an Array, accesses the memory directly, waiting for GPU work that uses the array to finish first.

See Choosing a resource storage mode for Apple GPUs, and Metal.PrivateStorage.

source
Metal.PrivateStorage — Type
Metal.PrivateStorage

The private storage mode (MTLStorageModePrivate): the memory is only accessible from the GPU, and indexing such an array from the CPU makes a slow copy, subject to allowscalar. Use it for data that only the GPU accesses, or to make sure that operations on an array execute on the GPU. Create private arrays with, e.g., MtlArray{Float32,1,Metal.PrivateStorage}(undef, n), or mtl(A; storage=Metal.PrivateStorage).

See also Metal.SharedStorage.

source
Metal.ManagedStorage — Type
Metal.ManagedStorage

The managed storage mode (MTLStorageModeManaged), which keeps separate CPU and GPU copies of the memory. Apple silicon GPUs don't need it, and MtlArrays don't support it: use Metal.SharedStorage instead.

source

Sharing memory with the CPU

Base.unsafe_wrap — Method
unsafe_wrap(MtlArray, a::Array, [dims]; [dev], [hazard_tracking], [cache_mode])
unsafe_wrap(MtlArray{T,N}, a::Array, [dims]; ...)
unsafe_wrap(MtlArray, ptr::Ptr{T}, dims; ...)

Wrap an MtlArray around host memory, without copying, so that it can be used on the GPU, e.g., in kernels or broadcasts. Apple silicon has unified memory, so the GPU operates directly on the original memory, and changes are visible from both sides. The array has shared storage.

The keyword arguments select the device (dev, defaulting to device()) and are passed to the Metal buffer: hazard_tracking and cache_mode, which take MTLResourceOptions values from Metal.MTL.

When wrapping an Array, the returned MtlArray keeps it alive, until the GPU is done using it. When wrapping a pointer, the caller has to make sure the memory stays valid for as long as the MtlArray is used. In both cases, the memory must not be freed or reallocated while it is wrapped (e.g., by calling resize! on the original array), and resizing the wrapper detaches it from the original memory.

GPU operations execute asynchronously, so synchronize (e.g., using Metal.synchronize()) before accessing the original memory on the host.

a = rand(Float32, 1024)b = unsafe_wrap(MtlArray, a)b .= sin.(b)        # executes on the GPU, updating `a`Metal.synchronize()
source
Base.unsafe_wrap — Method
unsafe_wrap(Array, arr::MtlArray, [dims])

Wrap a Julia Array around the memory that backs arr, without copying. This is only possible for arrays with SharedStorage, including host memory that was itself wrapped using unsafe_wrap(MtlArray, ...).

Warning

The returned Array does not keep arr alive. The caller has to keep a reference to arr for as long as the Array, or anything derived from it, is used; otherwise the Array may end up referring to freed memory.

Wrapping waits for pending GPU operations on arr. GPU operations execute asynchronously, so synchronize again (e.g., using Metal.synchronize()) before accessing the returned array after using arr on the GPU.

total_memory(dev=device())

Return the amount of memory, in bytes, that the GPU dev can use without affecting its performance: Metal's recommendedMaxWorkingSetSize. Apple GPUs share system memory with the CPU, so this is a part of it, not dedicated memory.

Buffers

Metal.jl's low-level buffer allocator, which MtlArray uses.

Metal.alloc — Function
alloc(device, bytesize, [ptr]; storage=PrivateStorage, hazard_tracking, cache_mode)

Allocate an MTLBuffer of bytesize bytes on device, initialized with the memory at the CPU pointer ptr if given, or with zeros otherwise. Free it with free. storage is Metal.PrivateStorage or Metal.SharedStorage; a buffer initialized from ptr cannot be private. hazard_tracking and cache_mode take MTLResourceOptions values from Metal.MTL.

Without a ptr, the buffer is padded to whole 4-byte words (and at least one): Metal does not support empty buffers, and GPUCompiler implements 8- and 16-bit atomics on the containing 32-bit word. Buffers initialized from, or wrapping, host memory must be non-empty.

source
Metal.free — Function
free(buffer::MTLBuffer)

Free a buffer allocated with alloc. Freeing a buffer twice is undefined behavior.
